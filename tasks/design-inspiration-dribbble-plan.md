# 明镜手机原型：Dribbble 参考驱动的结构与视觉改造方案

> 目标：将现有明镜原型从“多个业务块堆在同一页”改成用户能快速判断对象、优先级和下一步的移动端运营产品。方案同时处理信息架构、页面结构、组件、交互、文案层级和视觉风格，不把换色当作改版。
>
> 本文件是设计与实施方案，不代表本轮已经按此方案重新编码或完成浏览器视觉验收。检索日期：2026-10-09。

## 1. 结论与设计方向

建议采用“直播运营信号台”作为明镜移动端的设计方向：视觉沉着、重点清楚、按对象推进。界面首先回答四个问题：**现在要处理什么、涉及谁、当前卡在哪里、完成后下一步是什么。** 每个工作台从当日优先任务开始，随后呈现可处理队列；列表到对象详情保持主播/任务上下文；数据视图给出可读的结论和来源；次要说明不与操作争抢屏幕。

这个方向借鉴参考图中的留白、分区、纵向对象记录、状态色和固定主操作，但不把消费、课程、健身或医疗产品的整套装饰语言移植到运营工具。明镜的识别点应来自直播现场：主播阶段、开播状态、情绪/结业/激活信号、负责人、场次时间和明确的下一步，而不是泛化的彩色 KPI 卡片。

设计优先级沿用《原型设计原则.md》的顺序：**结构先于层次，层次先于视觉；可理解优先于一致、效率和装饰。** 用户此前明确允许为优秀原型打破旧文档结构约束，因此现有 49 个路由、页面归属和卡片排列都是待验证的设计材料，可以合并、拆分、精简或补充；业务含义、权限和数据口径不得为了视觉效果而丢失或擅改。

## 3. 项目专属设计语法

### 3.1 产品领域与设计签名

明镜的领域不是泛化的“SaaS 数据看板”，而是主播成长与直播运营协同。界面需要反复表达：主播阶段（签约/开播/成长/成熟）、当班状态（待开播/在播/收播）、成长信号（情绪/结业/激活）、直播场次与时间、归属团队/负责人、任务证据和结算口径。

**本项目的签名组件：主播工作对象条。** 它把“主播姓名/头像、成长阶段、当前信号、责任人、唯一下一步”放在一个紧凑但易读的对象上下文里。列表中展示摘要，详情页固定身份锚点，任何动作或深链都不丢失当前主播。这样，内容本身而不是颜色或装饰就能辨认这是直播运营产品。

### 3.2 初步视觉令牌（作为试点，不先全站铺开）

| 令牌 | 建议值 | 用途与原因 |
|---|---|---|
| 画布 `--stage` | `#F3F6F5` | 像干净的监看台表面，和纯白内容面形成轻微区分。 |
| 内容面 `--surface` | `#FFFFFF` | 长时间阅读、列表和表单使用稳定浅底。 |
| 主文字 `--ink` | `#14252B` | 高对比深墨色，承载标题、对象名和金额。 |
| 次文字 `--muted` | `#50636A` | 用于日期、来源、单位和说明；重要信息不降成淡灰。 |
| 分隔 `--line` | `#D9E2E0` | 优先用细线、间距和背景层次分组，少用厚边框/重阴影。 |
| 信号绿 `--signal` | `#0D6F67` | 用于当前选择、可执行/正常状态和主操作，不整页铺色。 |

语义色另有独立职责：预警琥珀 `#87510F`、风险红 `#A13D3D`、完成绿 `#226847`。颜色不能单独承载状态，必须同时配状态词或图标。最终值先在 P20/P30/P80 三个试点页测对比度和实际设备渲染，再决定是否全站采用；不直接照搬参考图的浅粉、浅紫或深色主题。

**字体与层级：** 使用适配简体中文的系统无衬线字体栈（优先 PingFang SC / Microsoft YaHei / Noto Sans CJK SC），同一界面不混搭装饰字体。页面标题 22–24 px，分区标题 18 px，对象/操作标题 16 px，正文 15–16 px，次要但用户必须读到的信息至少 14 px；产品内容不使用极小字塞入说明或单位。数值使用等宽数字特性，不引入代码字体。正文按自然语义换行，不能为保持单行而裁切姓名、状态、金额或动作。

**布局尺度：** 4 px 基准，常用间距 8/12/16/24/32 px；页面左右边距 16–20 px；主要操作热区至少 44 px，高频主按钮优先 48 px；内容卡圆角按功能分级（工作重点 18、列表组 14、控件 10），不用一个圆角/阴影套所有东西。阴影只表达浮层，不给每张卡加装饰性投影。

### 3.3 组件清单与使用规则

| 组件 | 职责 | 规则 |
|---|---|---|
| 移动页面壳 | 页面标题、返回、当前角色、底部主导航、内容滚动区 | 主导航文字标签持续可见；各角色只保留其高频 4–5 个入口。滚动仅发生在内容区，页面不左右移动。 |
| 今日优先事项 | 让用户立即知道先处理的任务 | 每页只突出一个主任务：对象、原因/期限、状态和明确动词 CTA；不使用整屏广告式 Hero。 |
| 主播工作对象条 | 列表扫描及详情上下文 | 姓名、阶段、信号/状态、负责人、下一步按固定顺序；长姓名/状态允许两行。 |
| 任务队列行 | 处理待办和进度 | 用垂直分组呈现“待处理/处理中/已完成”等真实状态；卡片或行中只放与当前动作有关的信息。 |
| 同级视图切换 | 切换工作范围/任务类型 | 2–4 个常用视图直显，文字清楚；不使用折叠标题/下拉框隐藏主内容。更多视图应拆分信息架构或进入明确的“更多”页面，不横向拖动。 |
| 过滤与搜索 | 定位对象 | 搜索放在列表前；有限筛选项在窄屏换行或进入筛选面板；保留筛选值和返回位置。 |
| 时间线 | 显示日程、沟通、任务历史和系统事件 | 最近/下一步最容易找到，时间、对象、状态同一行组；无横向周历，日期选择用明确的日期弹层/上下日切换。 |
| 指标解释行 | 解释经营/直播/结算数值 | 一个视图只呈现决策所需指标；数值紧邻单位、周期、来源；图表必须帮助比较或解释变化。 |
| 对象详情头 | 稳定对象、阶段和来源 | 详情页顶部固定对象与返回路径；可用内容分成同级视图或有标题的独立区，不把重要信息藏进 `<details>`。 |
| 固定操作栏 | 让当前合法主动作始终可达 | 手机安全区内贴底；每屏一个主 CTA，次动作至多一个；多步骤表单显示保存/下一步和错误反馈。 |
| 底部面板/弹窗 | 短选择、短确认、简短动作 | 弹窗不能超出手机容器；长文本使用全屏编辑面板且操作区固定；打开后焦点可达，关闭后回到触发动作。 |
| 消息/业务事件卡 | 区分普通对话与必须处理的事件 | 显示事件类型、主播/账单/任务对象、时间、未读/结果和直达动作；进入会话才清对应未读。 |
| 步骤进度 | 入驻、开通、培训等连续流程 | 只在真实顺序任务使用；显示当前步/剩余步和下一动作；不做装饰性数字序号。 |

## 4. 页面结构草图与交互样式

### 4.1 工作台：从“内容堆叠”变成“今日行动 + 工作队列”

适用于 P13/P20/P30/P40/P50/P60/P80/P93/P94。各角色共用阅读语法，不强求完全相同的内容；首页主任务由角色当天目标决定。

```text
运营工作台 · 今天                 通知
10月9日 · 我的主播 12 人

┌ 当前优先事项 ─────────────┐
│ 麦子 · 新人第4天 · 待回访          │
│ 原因：连续两天开播缩短             │
│ [记沟通]                 [看档案] │
└──────────────────────┘

待处理 4        已完成 2
[待处理] [全部] [已完成]
搜索主播……
• 麦子   情绪回访   今天 18:00 前   ›
• 椰果   结业跟进   已联系        ›
```

**改变点：** 先把一个任务说清，再显示队列；摘要只支持判断，不和待办争抢。需要完整经营数据时进独立数据视图。避免“三张等高 KPI 卡 + 三个同权内容大块”的通用仪表盘模板。

### 4.2 P30 经纪人首页：重点提示是产品信息，不是评审注释

以下两句是用户明确要求保留在产品页面的业务信息，不能挪到说明栏，也不能缩成不可读的小字：

> 回访第一：情绪、结业、激活三类今天必须碰。
>
> 价值：主播留存的第一道防线。

它们应成为首屏清楚可读的优先级说明（主句 16 px 左右，价值句 14–15 px），放在“今日回访”主任务块内；紧随其后是数量摘要和待回访队列。页面目标/适用角色/设计解释等制作说明另放原型评审侧栏，不混入上面两句真实工作语义。

```text
经纪人工作台 · 今天
┌ 今日优先回访 ────────────┐
│ 回访第一：情绪、结业、激活三类今天必须碰 │
│ 价值：主播留存的第一道防线。           │
│ 今天待回访 4 · 已联系 1                │
└──────────────────────┘
[待回访] [已完成] [签约漏斗]
主播对象条……
```

### 4.3 列表到详情：保持“同一对象”，不要增加层级迷宫

适用于 P21→P22、P31→P30D/P32、P41→P41D、P50→P51/P52、P60→P61/P62、P70→P71、P92→会话/业务详情。

```text
‹ 单主播
麦子   新人第4天   负责人：小周
当前信号：待完成结业评估

[概况] [规划] [复盘] [协作]
本视图只回答一个问题……

固定底部：[记录进展]
```

标签只用于确属同一对象下的同级视图，最多保持一行可读；长内容按纵向区块呈现。返回时恢复来源列表的筛选、滚动位置和主播对象。若视图的任务不同、操作不同，就拆成可直达的页面而不是继续叠标签/下拉。

### 4.4 数据页：由指标转成可行动的结论

适用于 P03/P13/P14/P70/P71/P82/P93。首屏显示周期、结论、异常/差异和责任对象；其次才给趋势图和明细入口。每个指标同时注明单位、期间和来源。排名、成员和账单转为纵向记录：名次/主播/数值/变化/操作清楚分行；不将桌面表格缩成手机宽度或增加横向滚动条。禁止为了“轻量”删去用户判断必需的业务字段。

### 4.5 日程/消息：沿时间组织，不让用户在横向轨道里找信息

适用于 P24/P40–P42/P50–P52/P81/P90–P92。以“今天/明天/更早”或日期标题做纵向分组；筛选类别直显；每条事件有时间、对象、状态和下一步。P50 用日期标题/日期选择器切换范围，记录按时间向下排列。P90/P92 将群聊、私聊、系统通知和业务事件标成不同类型。状态改变后更新对应的未读或队列计数，并保留回到原筛选与位置的路径。

## 7. 验收标准

1. **结构：** 每页能用一句话说清目标；首屏先出现当前任务或关键结论；页面分区按用户任务而非系统模块堆叠；主要业务区不是折叠/下拉控件的唯一内容。
2. **文本：** 评审说明、页面目标、设计价值、适用角色、AI/人工分工等制作备注不出现在产品画布，统一放评审侧栏。实际业务状态、单位、来源、风险、步骤和用户必须判断的信息仍在产品里，不能靠删文案“减密度”。P30 的两句业务信息必须留在产品首屏并清晰可读。
3. **手机布局：** 320×568、360×800、390×844、430×932 CSS px 下，页面不出现整页横向滚动、横向滚动条或横向数据表；长姓名、长中文、长金额和组合按钮允许折行或改为纵向布局。
4. **操作：** 主要按钮高度至少 44 px，标签明确说明结果；每屏只有一个视觉主动作，次动作收敛；浮层始终位于手机画布内；固定操作栏避开底部安全区，键盘出现时输入与保存仍可达。
5. **导航：** 主要页面视图直观可见；对象深链明确标出对象和来源；返回保留列表筛选、日期和滚动位置；旧 hash 有可验证的兼容映射；不以状态色或图标代替可读名称。
6. **状态：** 空、无结果、加载、错误、保存成功、无权限、完成、撤销/重做都有符合当前业务的反馈；失败时保留输入或明确恢复方法；未真实发生的后台行为不能展示“已完成”。
7. **视觉：** 层级靠字体、留白、对齐、分组和少量语义色建立，不靠所有模块加阴影；卡片形态按内容职责区分；图表与强调色必须带来判断价值。
8. **证据：** 代表路径由目标用户在不讲解的情况下操作；先记录用户实际点击和误解，再修改。单元测试/静态检查作为行为补充，不能冒充浏览器截图或可用性验收。Dribbble概念作品也不能替代真实用户验证。

## 8. 明确不采用的设计做法

- 不把每项内容都包成同样的圆角卡片，不为“现代感”统一加灰影或渐变。
- 不复制 Dribbble 首页的大幅商业 Hero、课程/商品横向货架、游戏角色插画、漂浮的加号按钮或暗色医疗皮肤。
- 不让用户左右拖动看完整名单/数据；不缩小字体去塞下桌面信息；不删除必须展示的字段。
- 不用下拉菜单或 `<details>` 隐藏主要页面和工作区；常用的同级任务视图应当被发现。
- 不把“适用角色/适用场景/页面目标/设计备注/评审说明”作为产品提示塞进用户界面；这些信息应在原型评审侧栏。
- 不为追求视觉效果更改业务计算、权限边界、资格门槛和消息/账单数据；需要调整时先提出明确决策及影响对象。
