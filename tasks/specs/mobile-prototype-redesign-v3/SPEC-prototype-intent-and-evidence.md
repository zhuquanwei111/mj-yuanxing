# Spec: prototype-intent-and-evidence

**Objective.** Make each prototype change answer a named question about a real user task and produce evidence for a design decision, instead of polishing pages because the calendar or old plan says to.

**Scope.** Before designing screens, define role context, device/context of use, highest-cost uncertainty, the task participants must complete, expected behavior, observation method, evidence to capture, and whether the HTML is a disposable test artifact or an evolving reference. Candidate hypotheses: a prioritized work queue reduces time to identify the next action; role-based navigation makes routes discoverable without a reviewer explaining them; vertical mobile records preserve all data without lateral scrolling.

**Requirements.** For each hypothesis, state what observation would disprove it. The moderator gives a realistic task and does not narrate the path. Record completion, wrong turns, hesitation, recovery, and participant interpretation; do not ask whether a screen “looks good” as the only measure. Freeze and name each tested version, then connect findings to a decision and next test.

**Acceptance.** Every high-priority flow in the final map has a user/role, task, hypothesis or reason for redesign, test method, observable pass/fail signal, evidence location, conclusion, and next decision. Test coverage accounts for role differences; the sample is expanded when risk or role variability requires it, rather than treating five people as a universal guarantee.

**Boundaries.** This module creates the research and decision contract, not new analytics, user data, or implementation code. Existing screenshot evidence is labeled historical and is never presented as a new test.
