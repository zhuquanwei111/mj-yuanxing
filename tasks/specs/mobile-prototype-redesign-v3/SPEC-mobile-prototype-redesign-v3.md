# Spec：明镜手机原型体验改版（V3）

状态：用户已于 2026-10-09 批准；当前按 tasks/plan.md 与 tasks/todo.md 由 Codex 增量实施。能力边界已获认可；**最高目标是做出优秀、可被真实用户理解和使用的手机原型；旧文档、旧页面数量、现有布局都不是必须保留的理由。**

## 目标

围绕明镜的真实业务任务，重新设计手机端的信息架构、视觉层级、文字呈现和交互路径，使老板、运营、经纪、培训、主播、组长、总监、平台管理等不同角色能看见“现在该处理什么、对象是什么、状态如何、下一步是什么”，并能在出错或返回时保留上下文。

这不是给 49 个索引逐一换皮。49 个页面索引和 34 处弹窗调用是盘点库存；方案必须逐项判断保留、合并、重做、移除或新增。若页面数量减少，先证明用户任务与必要信息仍有明确归属；若发现缺少的工作视图/状态，提出新增。原型结构可重组，不能为了符合旧计划而保留重复内容。

## 假设与已确定的用户要求

1. 当前阶段以手机端为主；桌面产品工作台仍后续处理。
2. 视觉/交互是本轮范围；不借此擅改业务规则、数据口径、计费或 AI 能力。
3. 产品界面不出现制作备注、评审目标、角色讲解或“AI/人工如何分工”等仅供评审者理解的元信息；评审说明可以放在外围目录/说明栏。
4. 文案按用途分类，不按字号一刀切。业务指令、任务引导、风险、状态、金额/单位、结果和必要帮助属于产品信息；重复、空泛或对任务无帮助的文案可精简；纯评审元信息移出手机界面。
5. P30 的“回访第一：情绪、结业、激活三类今天必须碰”和“主播留存的第一道防线”由用户明确要求留在产品界面，应在视觉上作为清楚的业务重点呈现，不能作为侧栏说明或隐藏脚注。
6. 现有页面矩阵与浏览器截图是基线证据，不是假设所有页面方案都已最终决定。报告必须分开标注源码推断、既有截图/交互记录和本轮后续新验收。

## 设计依据与取舍

设计原则以项目内的 [原型设计原则](../../../3_设计工作台/原型设计原则.md) 为核心，包括“信息架构先于界面”“结构 > 层次 > 视觉”“一屏一个主行动”“真实任务与坏路径”“按证据升级保真度”“观察行为而非问意见”。参考外部系统用于验证具体模式，不把它们的品牌视觉整套搬进明镜。

## 产品方向

**方向名称：直播运营信号台。** 设计来自真实领域对象：主播 roster、直播时段、风险信号、回访记录、任务交接、结业/签约进度、收益账期。让“对象 + 时间/状态 + 下一步动作”成为列表、队列、详情页的共同语法；让运营者读屏时像处理有序信号和交接记录，而不是在一堆同权卡片里猜重点。

视觉沿用当前产品的白/灰表面、深色正文与既有品牌蓝作为唯一主强调色候选；红/橙/绿仅表达风险、提醒、完成等真实状态。弱化或移除无语义渐变、重复阴影、紫蓝混合装饰色和整页同半径卡片套卡片。具体色值在视觉样稿中对照当前变量与对比度验证，不在规格阶段虚构品牌规范。

页面靠字体重量、空间和位置分组，减少线框与边框依赖。按任务类型使用熟悉模式：工作队列、名单/详情、时间线、分步表单、单对象工作区；只在业务关系确实相同时复用模式。全部文案采用真实中文、最长姓名/金额/状态和空数据样本检验。

### 文字与控件基线

- 页面标题 20–24px；区块标题 16–18px；正文/字段名 14–16px。12–13px 仅用于非关键时间、辅助元数据，保证对比度；“适用角色、页面目标、设计价值、AI 分工”等纯评审文字不因调大字号而进入产品画布。
- 控件不因密度而缩小文字或制造横排按钮挤压。主操作可视高度 44–48 CSS px；一般可触控区域至少 44×44 CSS px 为产品目标。W3C WCAG 2.2 AA 的 Target Size Minimum 是 24×24 CSS px，含间距例外；本规格采用更宽松的产品目标，Apple HIG 对其平台建议 44×44 pt。具体像素须用目标设备和浏览器复核。
- 以 4/8 基准节奏组织间距；同组内部近、组间明显远。不同角色的首页可采用不同密度，但密度必须服从任务，不让所有卡片等权。
- 主按钮写清动作和结果；一个视图只突出一项主要动作，最多一项清晰次动作。常用工具控制要有清楚名称/可访问标签、按下/焦点/禁用/完成状态。

## 核心体验要求

1. **先完成架构判断，再定样式。** 每个现有路由、页面块和弹窗标注角色、用户任务、入口/来源、对象、主行动、状态和返回目标；找不到真实任务的内容列为候选裁剪，不默认保留。
2. **页面结构不靠大块同权卡片。** 每页用一个明确任务标题、一个主操作、必要状态和顺序化内容构成。首页先行动队列，再提供分析/历史/设置入口；统计摘要不与待办抢同等视觉权重。
3. **导航可预期。** 底部导航只去高频顶层区域；页面内操作不混入底栏。进入对象详情后显示来源上下文；返回恢复对象、筛选、页签和列表位置。采用熟悉模式，不做任意层级限额；也不靠“三次点击内可达”作为质量指标。
4. **不用横向滚动让用户拼字段。** 表格在窄屏转换为带字段名的纵向记录或对象摘要 + 完整详情；所有原业务字段都在可发现路径上出现。不得靠 hover、裁切、缩小到难读、无标签图标或只显示数值来“解决”宽度。
5. **拒绝标题下拉作为主导航。** 主要内容默认呈现或通过可见 tab/分段按钮/直接命名入口切换；若下拉用作筛选器，标出当前选择并可恢复“全部”。Accordion 只用于少数非关键补充内容，且先以不折叠方案为对照。
6. **手机内弹层。** 34 个既有调用逐项判断是否仍应是弹层。简短选择可用底部面板；复杂编辑用适配可用视口的全屏编辑面板或独立步骤，不允许遮罩/弹窗溢出手机；键盘弹起时输入与保存/取消仍可达，关闭后回到原项并保留未提交内容。
7. **状态先于动效。** 重要动作需即时回应；每类页面检查默认、有数据、空、加载/处理中、部分完成、错误、无权限和完成状态中实际适用的情况。可撤销操作优先提供撤销；不可逆操作才增加确认。
8. **小字全原型分类。** 49 个既有页面全部扫描，包括当前截图没覆盖的页；每段文字标为业务信息、必要帮助、重复冗余、评审元信息或演示限制，记录保留/改写/合并/移位/移除及原因。

## 页面库存决策（所有路由适用）

每个现有索引提交如下记录：角色；用户任务；流量/来源；核心对象；用户当前的疑问；保留/合并/重做/移除/新增决定；必要信息及新归属；主动作；错误/空/完成状态；返回点；依据与可信度。合并时保留旧入口的明确去向或兼容演示链接，避免导航断路。若不同用户任务不可安全合并，保留独立视图。初步的 49 索引取舍见 [页面库存建议](page-disposition-proposal.md)；重点待核重复包括 P20/P21、P80/P81/P82、P13/P93、P94/P95、P60/P62、P90/P91/P92、P84/MY。

## 成功标准

- 49 个旧索引全部有 disposition 结论；34 个弹窗调用全部有“保留弹层/改底部面板/改专页/内联/移除”的结论；任何新增视图有明确用户任务和不替代的证据。
- 全局 IA 能让代表角色在入口、主任务、对象详情、动作反馈和返回路径间不靠讲解走通。用户任务测试记录成功/失败、错误、犹豫点和恢复情况，不用“觉得好不好”代替行为证据。
- P20、P21、P22、P30、P31、P40–P42、P80–P82、P94、P03 先做代表页面验证；首页 5 秒后测试者能说出页面主任务和下一步，但此测试只是诊断信号，不作为单独通过标准。
- 360×800、390×844、430×932 和 320×568 小屏压力测试：内容区无整页横向滚动、重要字段未裁切、姓名/中文段落/大金额可自然换行；用户无需左右拖动读全数据。
- 页面、底栏、操作栏、表单错误、结果、弹层符合可见状态与返回恢复要求；主操作触控区域目标达到 44×44 CSS px；对比度与键盘焦点按 WCAG 2.2 实测。任何平台不支持的状态要标出限制而非勾为通过。
- 产品画布不展示评审元信息或制作备注；P30 两句明确业务文案保留；所有冗余内容删改有归属说明。
- 高保真视觉只在 IA 和关键路径被证据支持后做。每轮原型要记录假设、方法、观察、证据、结论、下一步，并冻结用于测试的版本。

## 项目结构与验证命令

现有原型为单一静态 HTML，主文件是 `明镜/1_产品原型/明镜产品原型.html`；QA 外壳为 `明镜/1_产品原型/prototype-qa.html`；设计规格与证据放在 `tasks/`。本轮新增规格按 capability map 分文件存于本目录。无 package build 命令；后续执行采用：

- JavaScript 与 viewport 基础检查：`node tasks/check-prototype.mjs`
- 既有导航回归：`node --test tasks/navigation.test.mjs`
- 本地静态预览（仓库根目录执行）：`python -m http.server 8791 --directory 明镜/1_产品原型`
- 预览：`http://127.0.0.1:8791/明镜产品原型.html`；验收壳：`http://127.0.0.1:8791/prototype-qa.html`

基础脚本通过不代表视觉或点击验收通过。浏览器验证须保存路线、视口、截图、交互步骤和结果。

## 边界

- 始终：以用户任务为判断标准；将 49 个页面和 34 处弹窗当清单逐项审查；保留并突出用户明确点名的 P30 业务文案；说明每项采纳、合并和删除的原因。
- 本轮实施手机原型视觉与交互改版；不做桌面产品改版、后端/AI/业务规则改造或生产发布。
- 不做：为满足旧文档数量而保留冗余页面；把所有小字都搬到侧栏；用微缩字体、横向滚动、悬停或无标签图标藏信息；把已有截图测试描述成当前新验收。

## 未决问题（按推荐值推进，评审时可改）

1. P21 默认视图：推荐“主播名单”，因运营需要先选对象并行动；“动态”作为同级收件箱而非同页第二大区块。
2. P22 详情结构：推荐对象概要+下一步作为总览，趋势/规划复盘/协作成为显式可见入口；避免四个以上压缩 tabs 和折叠列表，视觉样稿需比较两种导航。
3. P94 组务：推荐“待处理 / 本组成员 / 本组数据”同级视图，默认待处理，计数只用于表示当前数量，不将所有内容塞回同页。
4. “抛弃型还是演进型原型”目前没有明示。推荐按可丢弃的验证原型管理；若此 HTML 还承担长期交付/实现蓝本职责，需在执行计划中单独设计可维护性策略。
