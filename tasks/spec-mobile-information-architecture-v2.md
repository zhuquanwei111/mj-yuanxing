## 1. 背景与目标

前一轮已处理手机宽度基础适配、弹层越界、页头制作说明迁移等问题。再次审阅后发现，部分页面虽然被拆成了若干内容块，但块与块之间没有明确主次；重要内容要滚动很久或展开原生折叠区才会发现。窄屏表格仍出现横向滚动条；页面内多个按钮尺寸、位置和权重不统一。

本规格只处理手机产品界面的信息组织、页面层级、响应布局、按钮与浏览交互。产品桌面布局以及业务规则、数据口径、接口、AI能力和真实服务接入不在本轮范围。所有现有业务字段和有效信息都必须保留并可在清楚的页面或入口中找到；允许改变顺序、分组、视图与导航，不得为了消除拥挤而删除信息。

**目标体验：** 用户进入任一工作台后，能快速回答“现在最需要处理什么、我在哪里看完整信息、下一步怎么做”；主播能在“今天”页迅速定位下一项行动；任何手机宽度下都无需横向拖动才能读完一条业务记录。

## 2. 能力地图与执行顺序

| 模块 ID | 责任范围 | 依赖 |
|---|---|---|
| `mobile-shell-controls` | 手机容器、页面层级、导航、按钮/触控区、窄屏数据呈现的共用规则 | — |
| `operations-home` | 运营工作台 P20、主播名单与动态 P21 | `mobile-shell-controls` |

构建顺序：共用规则 → 运营与主播高频路径 → 培训 → 组务 → 全原型逐页扫描。规格覆盖多个独立验证模块，先由需求方审阅本规格及能力边界，再由执行 Agent 开始改原型。

## 3. 现状问题与对应原则

| 问题 | 原型中的表现 | 设计原则 |
|---|---|---|
| 主次平铺 | P20 连续堆叠待办、四个同权指标、今日开播名单；P94 将指标、总监任务、风险、分配、主播名单连续放在一条页面流中 | 每页一个主任务；首屏先给当前待处理队列或下一步行动，概况作为辅助，名单/历史/分析用清楚命名的同级视图或页面入口承载 |
| 重要信息被埋 | P21 主播名单之后才出现“主播动态”，并使用折叠控件；用户难以发现事件视图 | “主播”和“动态”是两个并列工作视图，在页面顶部明确标名、显示数量/待处理数；进入动态后按时间和紧急度组织，并让事件直达对应主播或动作 |
| 过多折叠/深层查看 | 多页用 `<details><summary>` 隐藏整块名单、任务、排行、成长阶段或历史 | 不用折叠控件承载主要业务区、完整名单、统计表或页面主任务。用明确的页签/分段视图/直接详情入口切换；当前所选视图要持续可见。折叠仅可用于可选的短说明，且不得成为关键字段的唯一入口 |
| 详情层级与操作混乱 | P22 单主播卡片内放“生成规划、转交、记沟通、发消息”四个并列动作，资料和成长阶段再折叠 | 主播身份、当前状态和最相关风险组成稳定对象头；根据当前状态只突出一个主动作，常用次操作最多一个，其余放有明确标签的“更多操作”；资料、趋势、规划/复盘、协作记录通过同级视图访问 |
| 手机表格要求横滑 | P03 公会用量排行用多列 HTML 表格，窄屏出现水平滚动条，活跃主播和健康度字段被推到屏外 | 将表格每行重排为纵向排行记录，字段全部具备可见标签和值；不以裁切、横向滚动或极小字号解决宽度问题 |
| 按钮不合适 | 同一页面卡片里按钮高度、宽度、主次权重不一致，动作并排挤压内容 | 统一控件规格与主次语义；减少每张卡片上的同时可见动作，不缩字、不挤成窄列来塞按钮 |

以上不是只修截图中的局部。`prototype-sweep` 必须扫描全部已注册页面、AI/P41D/MY 等补充入口，以及页面内表格、状态控件、按钮和已有弹层。

## 4. 目标信息架构与页面方案

### 4.1 运营工作台 P20：待办是主线，概况为辅助

建议将页面组织成有连续阅读顺序的三个区域，而不是三张等权大卡：

```text
运营工作台 · 今天                     消息/通知
班次选择（保留当前班次）

优先处理                                  查看全部待办
最紧急/最临近的一项：主播、原因、截止/状态、直接处理
其余待办按紧急度排在同一队列，可继续滚动

今日概况                                  经营分析 ›
今日应播 10 · 已开播 6 · 在播 3 · 音浪 18.8 万
数字可点击进入对应名单/分析；不做四张同权大卡

今日开播                                  搜索/筛选
每行：主播与场次时间 → 当前直播状态/风险 → 进入档案
```

群发回执在发送后作为持久状态提示，不长期插入待办首位；待办清零时提供明确空状态和可继续的入口。工作台的指标不能抢在待办之前形成第二个焦点。完整数据仍可通过“经营分析”或指标入口访问。

### 4.2 我的主播 P21：名单与动态成为清楚的并列视图

在标题下设置清晰、可见的两项切换：“主播名单（人数）”和“主播动态（待处理数/未读数）”。选择状态清楚，两个视图都不需要先展开隐藏区。

- **主播名单：** 搜索和状态筛选在列表之前；列表行先显示姓名、直播状态/风险和一项最相关指标；点行进入 P22。卡片内不同时塞发消息、生成规划、转交等多个按钮，常用动作留一个，其他操作进入主播详情。
- **主播动态：** 作为事件收件箱展示时间线。事件类型、主播名、事件时间、当前状态完整显示；风险/结业/开播等事件有明确优先级与“查看主播/处理”直接入口。按“待处理/全部”过滤，事件不与完整主播指标卡混排，也不隐藏在名单末尾。
- 切换视图时保留搜索/筛选状态；从动态进入主播详情再返回时回到原动态位置。

### 4.3 主播 P80「今天」：唯一的下一步先出现

首屏依次给出：今天直播/任务状态、明确的一项“下一步”行动及主按钮、剩余待办计数或进度。主播动态/消息提示不得与下一项行动并列抢焦点。完整时间安排去 P81，昨晚复盘去 P82，资料与收益去 P84；入口要使用用户能理解的名称，不用制作性文案。页面间保持“今天 → 规划/复盘 → 返回今天”的稳定路径与主播对象。

P80 以现有业务信息重排，不增加虚构数据，也不删除原任务、回传、自检结果或风险提醒。较长的下一步说明完整换行；不要压缩到极小字体或横向滚动。

### 4.4 单主播详情 P22：围绕一个对象组织信息与操作

```text
主播姓名 + 当前状态 + 当前风险（如有）
一个主操作（随当前状态变化） + 一个常用次操作 + 更多操作

概况 | 趋势 | 规划与复盘 | 协作记录
当前选中区域的完整内容
```

名字、业务状态、风险、数据时间范围和关键值都要可读。四项操作不再平铺挤在对象资料卡里。操作移入“更多”时必须可发现，并且打开后仍在手机视口内。成长阶段、资料、趋势、规划/复盘、交接与沟通都要保留；将资料与成长阶段放在有名称的“概况/资料”视图，不依赖原生折叠条。每个视图的标题与主播对象同步，切主播不继承上一个对象的错误选项。

### 4.5 培训 P40/P41/P41D/P42：按“今天带教→学员→考核”走

培训首页 P40 是待办工作台：顶部用少量摘要标识“待带教、待评分、临近结业”，主体按紧急度展示带教/验收队列。不要把课目管理、全量考核历史、证书、学员名单全部塞进一条默认折叠的长页。提供清楚的“学员”“考核”入口，数量/状态可见。

- **P41 新人成长任务：** 先按学员/训练阶段找到任务；当前应完成的课目、完成状态、下一步和培训师验收动作集中呈现。切换学员/阶段使用可见的分段导航，进度与当前人始终可见。课目配置和历史从独立、命名清楚的入口进入。
- **P41D 学员档案：** 对象头、培训进度、待完成任务/成绩、沟通记录清晰分区；不将个人档案中主要信息藏在多个折叠块。档案内有明确返回任务/名单入口，并恢复之前的学员与滚动位置。
- **P42 带教与考核：** 默认先展示待评分/需补考队列，再提供历史/全部记录的同级视图。评分输入与结果反馈关联学员和课目；考核动作完成后状态持久可见。
- 同一学员/考核记录只在一个主位置呈现，避免首页待办、名单、考核历史重复堆叠全量内容。

### 4.6 运营组长组务 P94：先看待办，再分派，再看成员

推荐提供三个并列视图：“待处理”“本组成员”“本组数据”。默认进入“待处理”：总监下达、主播风险、脚本待审、任务分配回执放入一条有状态/负责人/下一步的队列，按紧急度排序。组长能在相关事项上直接完成或进入对应记录。

- “本组成员”显示全员名单，每行含姓名、直播/风险状态、负责人/任务状态；允许按状态筛选并直达档案。完整名单不放进隐藏折叠区。
- “本组数据”展示人数、开播率、今日音浪和环比，主次明确且字段/周期清楚；不要把四项数据都设计成同等突出的独立大卡。
- “分配任务”作为当前工作视图中的一个明确主按钮，表单字段完整，保存后在待处理队列和主播上下文中给出结果；不把已分配任务和待分配问题混在同一无状态列表。

### 4.7 窄屏排行、表格与其他宽数据

以 P03「公会用量排行」为模板，按行转为手机排行项：

```text
1  星曜传媒
本月 AI 用量       9.6 万次
活跃主播           具体人数
健康度             具体状态/数值
```

上述数据只是字段示例；必须使用原始行数据，不填造缺失值。其他 P 页面中的表格/矩阵/横向数据视图也按同一检查流程处理：确定每条记录的主标签，再把所有原列变成纵向标签/值或清楚的分段字段。可对很长的具体名称换行；如果列表字段很多，可让记录进入一条纵向详情页，但不得让用户通过左右拖动才能看到剩余字段。确实属于时间/空间坐标的视觉（如周历）需另作手机视图，不默认照搬桌面表格。

| `布局参考08.webp` | **重点采纳信息架构**：按日期/时段组织任务，通知列表使用分类过滤与清楚的事件条目；重复一级入口保持在底部 | 对应 P20 今日开播与班次、P21 动态、P94 待处理事项。日期/状态分组能帮助快速定位；通知类别筛选可沿用为“待处理/全部”等明确筛选 | 不因参考图为暗色就整体改暗色；不直接复制医疗预约的患者卡片、勾选完成方式或五个角色都相同的导航。角色一级导航按各角色真实任务保留既有含义 |

#### 参考项目与可借鉴的交互证据

以下资料用于校准模式选择，不要求把库或框架加进当前单文件原型：

- Android 官方移动布局指南将导航栏用于同层的 3–5 个一级目的地，并把 tabs 作为补充/子页面导航；因此 P21 两种视图和 P22 详情分区可以用同级页签，但不能把页签再套进无关层级。[Android：Layouts and navigation patterns](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns?hl=en)、[Android：Navigation bar](https://developer.android.com/develop/ui/compose/components/navigation-bar?authuser=89)
- Ant Design Mobile 是成熟开源移动 Web 组件项目，提供 List、Tabs、NavBar、TabBar、Button 等独立组件，可参照其组件边界和移动控件状态；本项目继续使用原生 HTML/CSS/JS，不为“参考”而引入 React 或组件依赖。[Ant Design Mobile GitHub](https://github.com/ant-design/ant-design-mobile)
- Ant Design 的 Tabs 说明将 Tabs 定位为相关视图之间的切换，适合 P21 的“主播/动态”与 P22 的详情分区；视图数量应有限、同属一个业务对象且标签完整可见。[Ant Design Tabs](https://ant.design/components/tabs/)
- Shopify Polaris IndexTable 展示了资源列表如何把对象、行操作和批量处理组织在一起，可参照“列表是用来找对象并采取行动”的结构；它不是手机端横向表格的照搬依据，P03 仍按本规格改为纵向排行记录。[Shopify Polaris IndexTable](https://polaris-react.shopify.com/components/tables/index-table?example=index-table-with-row-navigation-link)

采纳这些案例的判断标准是：能否让用户更快定位对象、理解当前状态、执行下一步，并且在手机窄屏完整读到信息。若只是更漂亮、增加装饰或占首屏面积，却没有改善任务完成路径，就不采纳。

## 5. 全局手机视觉与交互规格

### 5.1 页面层级与信息可发现性

- 每页只设一个首要任务/焦点。用顺序、空间、字号和明确的分组标题说明主次；不要让所有内容都使用相同卡片、边框和按钮权重。
- 主流程不超过三层：角色工作台 → 名单/工作视图 → 对象或任务详情。必要表单和确认不再额外引入一层通用弹窗套弹窗。
- 同级内容用有名称、当前选中状态和数量提示的页签/分段视图；内容项较少时用明确按钮直达页面。不得把“页面目标、名单、分析、历史、设置”等重要业务区藏在只有向下小箭头的 `<summary>` 后。
- 保留所有有效信息。允许调整默认首屏与浏览路径；不可删除字段、事件、历史、状态、结果或操作依据。标签和过滤器只能筛选，必须提供“全部/清除”与结果数量。
- 长名、长值、提示、风险原因和按钮文案可自然换行；同一对象的标题、数值、周期/单位必须保持对应。

### 5.2 无横向滚动和信息完整性

- 目标宽度 360、390、430 CSS px，页面主体不得出现水平溢出或水平滚动条；页面截图可见字段不能因容器裁切而消失。
- 不以 `overflow-x:auto`、`white-space:nowrap` 固定列、微缩字体、截断省略作为主要信息呈现方案。
- 对表格/指标网格逐列登记原字段，改版后逐项核对字段与值都能在纵向布局读到；不能以“换成卡片”为由遗漏列。
- 在开发者控制台/DOM 度量 `scrollWidth <= clientWidth`（允许图标/阴影的亚像素差异）；还需人工看截图，确保没有只在技术上无溢出但文字被裁掉的情况。

### 5.3 按钮与触控区

- 所有能执行动作的最小实际点击区域目标为至少 44×44 CSS px；紧凑的图标可以视觉较小，但外围触控区域不能小于目标值，且相邻触控区域不得重叠。
- 正文主按钮建议高度 44–48px，次按钮至少 40px 可视高度且触控区达标。页面/卡片操作优先“一个主动作 + 一个次动作”；其余动作放明确命名的更多菜单或对象详情。
- 按钮文案用动作+对象/结果表达（如“查看麦子的档案”“提交本次评分”），避免多个泛化的“查看/确定”。主要按钮在拇指可及位置；短屏或键盘弹出时仍可访问。
- 样式状态至少包含默认、按下、键盘焦点、禁用和已完成/处理中反馈。不能只靠颜色区别状态。

### 5.4 视觉一致性

- 延续当前产品黑白中性色；风险/警告/完成色只表达状态，不增加无语义装饰颜色。
- 使用清楚的四级文字层次：页面标题、区块标题、正文、辅助信息。业务正文以14–16px为主，关键数值和状态更突出；辅助文字不低于12px且保证足够对比度。不可把必需字段做成“视觉上像说明书脚注”的小字。
- 采用4px间距基线，但按关系拉开间距：相关字段紧凑、独立任务区明显分组；减少卡片内套卡片和重复边框。
- 页标题、返回、当前角色/对象上下文在各层级保持稳定；已确立的外围评审说明继续只留在评审侧栏，不回流到手机产品画布。
